### Handoff: стенд FreeSWITCH + SIPp для проверки recovery

#### 0) Цель текущего этапа
- Собираем натурный стенд для проверки штатного сценария FreeSWITCH recovery, описанного в официальной HA-документации SignalWire/FreeSWITCH.
- На первом шаге проверяется не полноценный HA с двумя одновременно работающими узлами, а упрощенный baseline:
  - один FreeSWITCH-процесс принимает звонок от абонента A;
  - FreeSWITCH бриджит звонок на абонента B;
  - на активном звонке FreeSWITCH будет аварийно остановлен через `fsctl crash`;
  - затем тот же FreeSWITCH запускается снова на том же адресе/порту;
  - recovery запускается явно через штатные команды FreeSWITCH.
- PostgreSQL, floating IP, keepalived/corosync/pacemaker и отдельная сетевая синхронизация на этом этапе не используются.
- Проверка `mod_demo_ai` на этом этапе еще не выполняется.

#### 1) Подходы и ограничения
- Продолжают действовать правила из `docs/development_approaches.md`.

#### 9) Проверка обычного звонка через FreeSWITCH
- Проверен базовый сценарий:
  - SIPp B: UAS на `127.0.0.1:6070`;
  - SIPp A: UAC с локального порта `6060`;
  - FreeSWITCH: `172.22.89.126:5060`;
  - dialplan bridge: `sofia/internal/${destination_number}@127.0.0.1:6070`.
- Команды использовались в такой логике:

```sh
sipp -sn uas -i 127.0.0.1 -p 6070 -m 1 -nostdin
sipp 172.22.89.126:5060 -sn uac -i 172.22.89.126 -p 6060 -m 1 -r 1 -nostdin
```

- Результат короткого звонка:
  - SIPp A/UAC: `Successful call = 1`, `Failed call = 0`;
  - SIPp B/UAS: `Successful call = 1`, `Failed call = 0`;
  - FreeSWITCH корректно принял INVITE от A и отправил INVITE на B.
- После проверки активных каналов нет:
  - `fs_cli -x "show channels"`: `0 total`;
  - `fs_cli -x "show calls"`: `0 total`.

#### 10) SQLite / recovery state
- В `/var/lib/freeswitch/db` созданы persistent DB:
  - `core.db`;
  - `sofia_reg_internal.db`.
- В `core.db` есть таблица `recovery`.
- На момент handoff активного звонка нет, поэтому:

```sql
select count(*) from recovery;
```

возвращает `0`.

#### 11) Что не завершено
- Не завершена проверка долгого удерживаемого звонка.
- Попытка запустить долгий вызов через shell background оказалась неудобной из-за quoting PowerShell/WSL.
- Попытка использовать `sipp -bg` для UAS завершилась сразу; активных SIPp-процессов после этого не осталось.
- На момент handoff `pgrep -a sipp` ничего не возвращает.
- Следующий шаг: стабильно запустить долгоживущий SIPp UAS/UAC, удержать активный bridged call и проверить:
  - `fs_cli -x "show channels"`;
  - `fs_cli -x "show calls"`;
  - строки в `core.db.recovery`;
  - затем выполнить `fsctl crash`, перезапустить FreeSWITCH и попробовать штатный recovery.

#### 12) Практическая рекомендация для следующего шага
- Для долгого сценария лучше не мучить встроенный `-sn uac/uas`, а создать минимальные XML-сценарии SIPp с явной длинной `pause`.
- Это позволит:
  - держать A/B legs достаточно долго для `fsctl crash`;
  - задавать таймауты recovery явно;
  - собирать message/error logs предсказуемо;
  - не зависеть от того, как embedded scenario интерпретирует `-d` в конкретной версии SIPp.
