### Handoff: текущее состояние проекта `mod_demo_ai`

#### 0) Постановка задачи / цель проекта
- Цель: создать прототип (MVP) управляемого восстановления звонков FreeSWITCH в схеме резервирования 1+1, позволяющий после failover корректно поднять вызовы и переустановить ключевые SIP/SDP-параметры (адреса/медиа) без форка исходников FreeSWITCH.
- Подход: реализовать надстроечный модуль `mod_demo_ai`, который оркестрирует штатный recovery-пайплайн FreeSWITCH (`sofia recover`) и добавляет сервисные API-команды для последующей перенастройки медиа/сигнала (renegotiation), действуя исключительно через публичные API/события ядра и модулей.
- Ограничения: без правок в дереве `examples/fs` (исходники FreeSWITCH) — только собственный модуль и инфраструктура сборки/навигации; изменения — точечные и обратимые.
- Критерии готовности MVP:
  - имеется API-команда, поднимающая целевую сессию из таблицы `recovery` и инициирующая медиаперенастройку (в проекте: `demo_ai_takeover <uuid> <profile>`);
  - подтверждено восстановление сессии при изменившихся адресах за счёт renegotiation базовых параметров;
  - актуализирована документация (данный handoff, карта вызовов/SQL) и рабочая сборка модуля без ошибок.

#### 2) Где находится FreeSWITCH и как он используется
- Исходники FreeSWITCH находятся в: `examples/fs`.
- В этом проекте FreeSWITCH используется в двух режимах:

  - локальные исходники `examples/fs` — для IDE-навигации/индексации.
- Важный момент: FreeSWITCH **не подключен к обычной сборке модуля** как полноценный subproject.

#### 3) Подключенные библиотеки и механизм подключения

#### 4) Что важно про `bootstrap/configure`

- Эти autotools-флаги сами по себе не переносятся автоматически в CMake-модель CLion, поэтому include/cflags были продублированы в `freeswitch_ide`.

- Цель `freeswitch_ide` предназначена для IDE. Ее фактическая сборка может падать на отдельных файлах FreeSWITCH (это не блокирует навигацию).

#### 7) Текущий фокус (recovery, без правок кода)
- На текущем этапе идет анализ механизма восстановления звонков (`sofia recovery`) без внесения изменений в код.
- Подтверждено по коду и текущей логике: восстановление опирается на сохраненное состояние канала/метаданные recovery и пытается поднять вызов в том же виде, в котором он был зафиксирован.
- Практический эффект: в SIP/SDP части используются прежние адреса/параметры, что ограничивает схему резервирования `1+1`, если после failover адреса узла меняются.
- Следующий шаг (в обсуждении): выбрать целевую функциональность восстановления для `1+1` (какие поля должны пересчитываться/переопределяться при recovery), затем перейти к проектированию точечных изменений.

#### 8) Структура обработки команды `sofia recover` (карта связей по исходникам)

##### 8.1 Точки входа команд
- Профильная команда: `sofia profile <profile> recover [flush]`
  - файл: `examples/fs/src/mod/endpoints/mod_sofia/mod_sofia.c`
  - ветка `if (!strcasecmp(argv[1], "recover"))` (внутри обработки `profile`-команд), вызов `sofia_glue_profile_recover(profile, ...)`.
- Глобальная команда: `sofia recover [flush]`
  - файл: `examples/fs/src/mod/endpoints/mod_sofia/mod_sofia.c`
  - ветка `else if (!strcasecmp(argv[0], "recover"))`, вызов `sofia_glue_recover(...)`.
  - при обычном recovery (не `flush`) формируется событие `MY_EVENT_RECOVERY_RECOVERED`.

##### 8.2 Переход из mod_sofia в glue-слой
- `sofia_glue_recover(switch_bool_t flush)`
  - файл: `examples/fs/src/mod/endpoints/mod_sofia/sofia_glue.c`
  - обходит профили (`list_profiles_full`), для каждого вызывает `sofia_glue_profile_recover(profile, flush)`.
- `sofia_glue_profile_recover(sofia_profile_t *profile, switch_bool_t flush)`
  - файл: `examples/fs/src/mod/endpoints/mod_sofia/sofia_glue.c`
  - если `flush`: `switch_core_recovery_flush(SOFIA_RECOVER, profile->name)`
  - иначе: `switch_core_recovery_recover(SOFIA_RECOVER, profile->name)`.

##### 8.3 Core recovery pipeline (БД + callback)
- `switch_core_recovery_recover(const char *technology, const char *profile_name)`
  - файл: `examples/fs/src/switch_core_sqldb.c`
  - шаги:
    1. `SELECT technology, profile_name, hostname, uuid, metadata FROM recovery ...` (фильтр по `runtime_uuid != switch_core_get_uuid()`, с учетом `technology/profile_name`).
    2. Для каждой строки вызывается `recover_callback`.
    3. После прохода выполняется `DELETE FROM recovery ...` по тем же фильтрам.

##### 8.4 Что делает `recover_callback`
- файл: `examples/fs/src/switch_core_sqldb.c`
- по строке recovery:
  - парсит XML из `metadata`;
  - находит endpoint-interface по `technology`;
  - вызывает endpoint-specific `recover_callback`;
  - при успехе выставляет флаги канала recovery (в т.ч. `CF_RECOVERING`, при bridge — `CF_RECOVERING_BRIDGE`),
    вызывает `switch_core_media_recover_session(session)`, переводит канал в `CS_INIT`, запускает thread session.

##### 8.5 Endpoint-specific часть для SIP (mod_sofia)
- `sofia_recover_callback(...)`
  - файл: `examples/fs/src/mod/endpoints/mod_sofia/sofia_glue.c`
  - восстанавливает SIP-специфичное состояние (`tech_pvt`, профиль, параметры диалога/направления) на основе сохранённых переменных канала.

##### 8.6 Где формируются записи для recovery
- В mod_sofia есть точки `switch_core_recovery_track(session)`:
  - файл: `examples/fs/src/mod/endpoints/mod_sofia/sofia.c` (несколько мест);
  - также вызов в `examples/fs/src/mod/endpoints/mod_sofia/sofia_glue.c` (для inbound-сессии).

##### 8.7 Ключевой вывод для задачи 1+1
- Текущий recovery-путь ориентирован на восстановление из ранее сохранённого снимка вызова (SIP/SDP/channel vars).
- Поэтому при смене адресов после failover (схема `1+1`) механизм по умолчанию пытается восстановить вызов со "старыми" адресами/параметрами, что и является целевым ограничением для последующей доработки.

#### 9) Дополнительные подтверждения по SQL-модели звонков (core DB)

##### 9.1 Где хранится последнее исполненное приложение диалплана
- Последнее приложение и его аргументы фиксируются в таблице `channels` в полях:
  - `application`
  - `application_data`
- Эти поля обновляются на событии `SWITCH_EVENT_CHANNEL_EXECUTE` (обновление строки канала по `uuid`).

##### 9.2 Как формируется связка каналов в один звонок
- На событии `SWITCH_EVENT_CHANNEL_BRIDGE`:
  - обоим каналам выставляется общий `call_uuid`;
  - в таблицу `calls` добавляется строка связки `caller_uuid <-> callee_uuid`.
- На событии `SWITCH_EVENT_CHANNEL_UNBRIDGE`:
  - `call_uuid` у каналов сбрасывается обратно к собственному `uuid`;
  - строка связки удаляется из таблицы `calls`.

##### 9.3 Где читается «картина звонка»
- Представления:
  - `basic_calls`
  - `detailed_calls`
- Они собирают A/B-ноги через join:
  - `channels a` + `calls c` + `channels b`
- В `detailed_calls` присутствуют также `application/application_data` для обеих ног (`a_*` и `b_*`).

##### 9.4 Ограничение текущей core-модели для multi-channel сценариев
- В `switch_core_sqldb.c` нет отдельной SQL-сущности «конференция».
- Текущая модель `calls` в core DB — в первую очередь парная A↔B-связка (bridge-пара).
- Для сценариев с несколькими каналами в одном логическом звонке (`conference`, `eavesdrop`, `threeway/attended transfer`) этой модели недостаточно как полного графа связей; это нужно учитывать при проектировании расширения recovery.

#### 10) Что подтвердилось по `mod_conference` и отражению в каналах/БД

##### 10.1 Как собирается конференция в модуле
- Точка входа в приложение: `conference_function` в `examples/fs/src/mod/applications/mod_conference/mod_conference.c`.
- Регистрация dialplan app `conference`: `SWITCH_ADD_APP(..., conference_function, ...)` в `mod_conference_load`.
- При входе в app канал получает флаг `CF_CONFERENCE`; модуль далее находит/создает объект конференции (`conference_new`) и добавляет участника.

##### 10.2 Какие признаки участия ставятся на канал
- На уровне канала выставляются переменные, в т.ч.:
  - `conference_name`
  - `SWITCH_RFC7989_APP_SESSION_ID_VARIABLE` (UUID конференции)
- На уровне участника (`conference_member.c`) выставляются, в т.ч.:
  - `conference_member_id`
  - `conference_moderator`
  - `conference_ghost`
  - `conference_recording`
  - `CONFERENCE_UUID_VARIABLE`
  - `conference_call_key` (очищается при выходе участника)

##### 10.3 Как это попадает (или не попадает) в core DB
- `mod_conference` не пишет напрямую SQL в core DB (`switch_cache_db_*` в модуле не используется).
- Отражение в таблице `channels` идет косвенно через core event-pipeline:
  - на `SWITCH_EVENT_CHANNEL_EXECUTE` обновляются `channels.application` и `channels.application_data`;
  - поэтому выполнение app `conference` видно как «последнее приложение канала».
- Таблица `calls` по-прежнему обновляется только через `CHANNEL_BRIDGE/UNBRIDGE`, поэтому membership конференции как граф участников в `calls` напрямую не моделируется.

##### 10.4 Где брать детализацию по составу конференции
- Для состава/состояния конференции модуль опирается на собственные структуры и custom events (`CONF_EVENT_MAINT`, `add-member`/`del-member`, `conference_event_add_data(...)`).
- Практический вывод: для recovery multi-channel сценариев (`conference`) потребуется отдельная модель корреляции участников, а не только существующая A↔B модель `calls`.
